# hk-dsl documentation

**hk-dsl is a general-purpose Python DSL for AMD GPU kernels on RDNA and CDNA,
with build-time gates against silent tile-level errors (spills, missing waits,
MFMA hazards).** Today its largest end-to-end gains are on Radeon (RDNA3 and
RDNA4), where its kernels plug into vLLM and SGLang.
[What it is and is not](positioning.md) has the comparison with Triton,
FlyDSL and AITER, the supported hardware, and where the numbers come from
([the scorecard](performance/scorecard.md)).

## Start here

Five pages, in order, take you from nothing to a kernel that is checked for
correctness and timed against `torch.compile`:

1. [Getting started](getting-started.md): install, a first kernel from a
   template, checking it, and a kernel written by hand.
2. The templates: [elementwise and rowwise](templates/elementwise-rowwise.md)
   (the math of an element or a row) and [GEMM with an epilogue](templates/gemm.md).
   Start here whenever one fits.
3. [hk.check](check.md): resources, correctness against torch and speed
   against `torch.compile`, in one command, after every edit.
4. [The language](language.md): what a kernel body is written in, for when
   no template fits.
5. [The API reference](api/README.md): every public name, generated from the
   code; [hk.math](api/hk.math.md) is the list of elementwise functions.

Coding agents: start from [llms.txt](../llms.txt) and the
[hk-kernel skill](../skills/hk-kernel/SKILL.md) instead.

## Why this exists

Fast tile kernels for AMD GPUs can be written in C++, as HipKittens shows.
Three things stood between that and a faster model. The serving engines do
not use such kernels on a Radeon; at the tile level the kernels fail
silently; and writing and tuning them by hand is slow. This section takes
each in turn, with what hk-dsl does about it and where it stops.

### The engines leave Radeon on slow paths

vLLM and SGLang are tuned for Instinct. On a W7900D (gfx1100), hk's routes
replace these calls, each one only for the shapes where hk's kernel measured
faster than what the engine runs:

- **SGLang's linear layers**, which are `F.linear` on ROCm (hipBLASLt)
  ([SGLang](history/24-sglang.md)).
- **SGLang's MoE**, which does not run on gfx1100: sgl_kernel's top-k
  faults. hk's patch replaces the top-k and the expert GEMMs
  ([SGLang MoE](history/25-sglang-moe.md)).
- **vLLM's 4-bit linear layers**, a Triton AWQ kernel on ROCm
  ([4-bit weights](history/22-int4.md)).
- **vLLM's MoE**, Triton's `fused_moe` ([MoE](history/21-moe.md)).
- **vLLM's decoder attention**, Triton's `unified_attention`, through hk's
  attention backend. It is off by default
  ([integration](integration.md#the-decoder-attention-backend)).

Each patch can be turned off by an environment variable, sends each shape to
the kernel that measured fastest for it, and keeps to the CUDA-graph contract
([integration](integration.md)). A model nobody tuned for gets its linear
layers' routes measured at its first start
([chapter 35](history/35-any-model.md)). What the routes gain end to end on
Radeon will be published with the RDNA scorecard.

On an MI355X (gfx950) the engines are tuned for the card through AITER. There
hk's default routes give DeepSeek-V4.1-Flash on vLLM (TP2) about +5% on
8k-token prefill over a stock vLLM that already uses AITER's tuned paths
([the scorecard](performance/scorecard.md)).

### Why not HipKittens' C++ directly

HipKittens' `include/rdna3` is about 12,000 lines of tested C++. Using it
meant writing C++: `kernels/rdna3/attn/fwd/attn.cpp` is 1108 lines with 18
`#define` knobs, and retuning meant editing macros, `make clean`, rebuild,
remeasure. vLLM and SGLang could not touch it.

hk-dsl keeps HipKittens as the backend: its tiles, MMAs and waits, in the C++
it generates. In front of it are a typed Python layer, an MLIR dialect whose
passes check and derive what the C++ left to the author, a tuner, and the
engine layer. The knobs are Python parameters a tuner searches, and a kernel
becomes a torch op, then an engine patch, in a few lines. A kernel written in
hk-dsl compiles to that C++ and runs at its speed, no faster
([Phase 4](history/03-phase-4-attention.md),
[Phase 3](history/02-phase-3-gemm.md)). One 59-line strip kernel is RMSNorm,
LayerNorm, softmax, the weighted RMSNorm and the fused add + RMSNorm
([strips](history/27-strips.md)).

### Why not only Triton or FlyDSL

Each covers part of the space:

- **FlyDSL** has a GEMM dispatcher with instruction-level control. It has no
  attention on gfx11, because its flash attention stages K/V through a
  global-to-LDS load gfx11 does not have.
- **Triton** schedules the tile itself, and is much cheaper to write. The
  attention torch runs on ROCm is aotriton.
- **hk-dsl** gives tile-level control on RDNA3 and RDNA4 as well as CDNA,
  attention included, with the build-time gates below.

So hk-dsl is built to sit beside them. A route table may name FlyDSL's
kernel, HipKittens' own or the engine's for the shapes where they measured
fastest ([FlyDSL on the routes](integration.md#flydsls-gemm-as-an-optional-path)).

### The traps

At the tile level the compiler can hoist an MMA above the wait that guards
it, a register spill reorders against hand-placed waits, an operand in the
wrong layout takes eight times the instructions, and on CDNA4 an
asynchronous copy into shared memory races the barrier after it. Each of the
first three cost days to find, and none produces a diagnostic. In hk-dsl each
is either impossible to write or refused before the kernel runs:

1. **`s_waitcnt` carries no register dependence.** The compiler will hoist a
   WMMA above the wait that was supposed to guard it. Results are randomly
   wrong, `ScratchSize` is 0, and nothing is reported. The translation binds
   the fragment with a volatile asm after every wait — you cannot forget to
   ([IR](ir.md#translation)). CDNA4 is no different: on an MI355X, every LDS
   GEMM built without the bind returned NaN ([chapter 29](history/29-cdna.md)).
2. **A VGPR spill is silent corruption, not slowness**, because this library
   hand-places `s_waitcnt` and scratch traffic reorders against it.
   `k.build()` parses `-Rpass-analysis=kernel-resource-usage` and *refuses to
   return* a spilling kernel ([runtime](runtime.md#the-resource-gates)).
3. **Only row-layout 16-bit operands reach `ds_read_b128`**; column layout
   degrades to 16 scalar `ds_read_u16`, eight times the instructions. The
   passes flag it while tracing, not at benchmark time ([IR](ir.md#passes)).
4. **On CDNA4, a copy from global memory into LDS is still in flight at the
   barrier after it.** It counts on `vmcnt`, gfx950's back-off barrier makes
   LLVM put no wait before `s_barrier`, and the reads after it are inline asm
   that LLVM's wait insertion cannot see. The first LDS GEMM on an MI355X gave
   a different wrong answer on each run. The translation now follows every
   such copy with its wait ([the race](history/29-cdna.md#the-race)).

`python -m hk.runtime.cocheck` runs the resource, wait and MFMA-hazard gates on any AMDGPU
code object, hk's or not ([runtime](runtime.md#any-code-object-cocheck)).

### Arch facts as data

The arch facts that used to live in `RDNA.md`, kernel comments and notebooks
are now data: `target/gfx1100.py`, `gfx1201.py`, `gfx942.py` and `gfx950.py`
for Python, and `mlir/lib/Target/Target.cpp` for the passes, with a test that
the two tables agree field by field. Two examples: on gfx1100 the VGPR granule
is 24, so occupancy 6 needs ≤240 registers, not ≤256; on gfx9 lgkmcnt has
4 bits, so a derived wait above 15 is emitted as the cap.

An op that the library does not implement for the requested dtype is the same
kind of late failure, so it is caught the same way: `gelu` on a bf16 tile
raises while tracing rather than producing `undefined hidden symbol` at the end
of a 30-second compile.

Where each of these is enforced: the translation ([IR](ir.md#translation)),
the resource gate ([runtime](runtime.md#the-resource-gates)), the passes
([IR](ir.md#passes)) and the target tables ([IR](ir.md#target-facts)).

### Where it stops

- **One GPU of each kind.** Every number is from one W7900D or one MI355X.
  The engine results are mostly the W7900D's; on the MI355X only vLLM has
  been measured end to end; gfx1201 runs the GPU tier on an R9700, and three
  vLLM routes are on by default there
  ([integration](integration.md#on-by-default-and-turning-it-off)), and gfx942
  has only been compiled for ([CDNA3/4](design/cdna.md)).
- **Some kernels lose.** Where hk's kernel is slower than the engine's for a
  shape, the routing leaves that call to the engine: on the W7900D the MoE
  GEMM above 256 tokens and the W4A16 GEMM at 1-4 tokens; on the MI355X most
  GEMMs, norms and bf16 MoE GEMMs against AITER's tuned ones, so hk's
  unquantized-linear and bf16 MoE routes do nothing there. [Performance](performance.md#a4-losses-and-limits), a
  dated record, lists the losses as they were measured, for
  [CDNA4](performance.md#b4-losses-and-no-headroom-findings) as well.
